## Accepted product and visual direction

Clinician/hospital B2B iPhone assistant for the healthcare competition: ambient documentation, intelligent workflows, triage support and hospital operations with privacy-focused open-weight models.

- One conversational workspace with automatic capability routing. The current router and responses are fixtures; arbitrary natural-language understanding is a backend task.
- Seven capabilities: briefing/timeline including medical/family/social history; ambient scribe and editable note; clinical possibilities with evidence/gaps; chest X-ray; medication interactions; autonomous synthetic prescribing; follow-up tasks.
- Autonomous prescribing intentionally has no clinician approval gate in the supported synthetic case. It still blocks missing inputs/stale checks, records sources and creates an immutable simulation receipt. Preserve that accepted behavior.
- Monogram-first liquid glass, pale grey canvas, subtle blue wash replacing the supplied Oria pink, charcoal type and selective Arc progress/source effects. Read [design direction](design-direction.md) and [UI specification](ui-specification.md) before changing the design. Supplied PNGs are in `docs/references/`.
- English baseline, bounded Malay/English/Mandarin Manglish demonstration. Current dialogue is scripted; real STT/TTS/S2S and code-switching capability have not been demonstrated.
- Baseten cloud is the intended inference platform, with hybrid deployment later. MedGemma is intended for medical/multimodal work; Gemma 4 is a candidate to evaluate, not a deployed model. Unsloth is intended for potential training. Budget was described as ample. Deployment, privacy/compliance and model capability still need actual evaluation.

For feature details, consult [PRD](prd.md), [storyboard](demo-storyboard.md) and [fixture plan](ui-fixture-plan.md) as needed. Proposed hospital ops demo flows (discharge, guarantee letter, ward view, evidence answers) are ranked in [ops demo flows](research/ops-demo-flows.md).

Findings to act on:
- **Cold start is 9–16 minutes** on the GPU boxes (vLLM start-up and torch.compile dominate); Laya's is 31 s. A request held open through a wake had its connection reset, so the Worker must wake a box, poll `/health`, then call it, and the demo warm-up starts at least 15 minutes early.
- **TTS speed.** Measured 1 Oct at the rated settings: plain VoxCPM took 2.0–2.8× the audio's length (a 45-character sentence, 4 s of audio, took 8–11 s) and 1.3–1.7× compiled (`day2-fast`, `wn4gj11`). Production is now `day2-nano2` (`qe9pll5`, promoted 1 Oct): Nano-vLLM-VoxCPM (CUDA graphs over the whole step) makes a sentence in about 1 s on the box (≈ 0.3× real time) and sends MP3 (49 KB instead of 420 for 4.5 s), so a short sentence reaches Malaysia in about 2.5 s; `day2-fast` and `day1d` are kept for rollback. Box ② now takes about 25 minutes to start (a 17 GB image, two Python environments on 4 CPUs). All four check sentences (en, ms, zh, the 999 line) were heard back word for word by the ASR. 4 `inference_timesteps` (uncompiled) only brought it to ≈ 1.5 and is unrated by ear. Each LM step makes 160 ms of audio and the L4's bandwidth allows about 26 ms per step, so the remaining time is VoxCPM's Python loop, not the GPU. Sona Care's voice mode reads answers in this voice anyway (`care.speak`, `apps/care/features/assistant/sona-voice.ts`): sentence by sentence, each kept in the phone's cache so a replay is instant and gap-free; a first sentence not ready in 8 s is read by the phone's voice, labelled, while the rest is still made for next time. Next for speed: profile VoxCPM's generation loop, or a faster GPU (a new deployment, so ask first), then streaming generation.
- **Tool calls:** route with a system instruction and `tool_choice` auto. `tool_choice: "required"` is not enforced while the gemma4 reasoning parser is on.
- **Laya runs on its own CPU box**, not inside box ①: a container gets one port, and the classifier does not need a GPU. Move it beside Gemma behind a proxy only if 0.5 s misses the budget.
- **Deploy gotchas:** a second `baseten model push` to a model is not promoted, so push with `--environment production`. Box ② loads VoxCPM2 straight onto the GPU (`voice/data/gateway.py`) because its fp32 checkpoint overflows the box's 11.5 GiB of RAM. The vLLM image's torch 2.13 has no torchaudio release, so voxcpm is installed without its pins. fastapi 0.142 (29 Sep) breaks laya-serve, so it is pinned to 0.141.1.
- **Adapter** (`packages/api/src/baseten-models.ts`, tests beside it): the Worker uses it when `BASETEN_API_KEY` is set (`apps/server/src/context.ts`; empty keeps every answer a labelled fixture). **Wake before calling** (1 Oct): the Worker no longer waits 30 s on a cold box.
